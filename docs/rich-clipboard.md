# Rich clipboard history

Clipboard history keeps its existing native SQLite opt-in, pins, retention choices, text credential filtering, and fail-closed paste target checks. On macOS, it additionally captures supported image originals and local file URL references after the user enables history. Browser-only previews do not capture the clipboard.

## Native contract

- Existing copy, paste, delete, clear, enable, retention, pin, and full-text commands retain their names and arguments. `paste::paste_text(app, text)` retains its signature for snippets and other callers, delegating to the same guarded payload paste path.
- `search_clipboard_history({query,limit,kind?})`: `kind` is omitted/null for all entries, or `text`, `image`, or `files`. Filtering occurs before the limit. Result fields: `id`, `text` (at most 500 Unicode characters plus ellipsis), `capturedAtMs`, `pinned`, `kind`, `mimeType` (nullable), `byteSize`, `width`/`height` (nullable), `fileCount`, and `available`. Original image bytes and file URL arrays are not returned by search. File labels are local paths; `available` is `null` (unknown) for files and `true` for text/images. Search reads only stored metadata and never loads file URL payloads or checks mounted volumes. Existing optional/nullable frontend availability fields remain compatible; no availability-check API is added.
- `get_clipboard_history_entry_preview({id}) -> string`: selected image only, returns a downscaled PNG data URL. Register this new command in `lib.rs`. Only one preview decoder runs at a time; contention returns a retryable notice. Work runs on a blocking worker, and disable/clear/delete generation changes invalidate a pending preview.
- `get_clipboard_history_settings` adds nullable `captureNotice`, explaining unsupported formats, limits, or pins filling storage. This is an in-process capture notice, not a durable error log. Storage failures retain the existing `persistenceError` behavior.
- `get_clipboard_history_entry_text` rejects image/file entries instead of handing snippet creation an image label or path preview.
- Add `NSPasteboardItem` to existing `objc2-app-kit` features. Image PNG/JPEG/WebP/TIFF, base64, Foundation NSArray/NSData/NSString, Tokio, and rusqlite dependencies suffice.

## Frontend integration

Mount `ClipboardTypeFilter` above the clipboard list with controlled `value` (`all|text|image|files`) and `onChange`. Pass the selected filter to native search. The component uses an accessible native select.

Mount `ClipboardEntryPreview` for the selected entry with `{id,content,kind,mimeType,byteSize,width,height,fileCount,available}`. The clipboard workspace presents a left list and a right detail pane with independent scrolling. A single click selects; Enter or double-click copies. Text details fetch the full original text, retaining line breaks; lists retain bounded previews. It loads a thumbnail only for a selected image in the native runtime, ignores late responses after selection changes or unmount, and offers a non-destructive retry. Other entries show text/file metadata and missing-reference guidance without reading file contents. Native copy/paste checks file availability independently of the displayed state; an unknown value is not a missing-file indication.

Propagate rich metadata through the native provider mapper and command item data. Offer Save as Snippet only for text entries. Settings explains formats, limits, privacy boundaries, and capture notices. New localization entries are supplied in `apps/desktop/src/clipboard/rich-localization.json` for the shared catalog owner to merge.

## Storage, privacy, and reuse

| Content | Capture and reuse |
| --- | --- |
| Text | Original UTF-8 text, at most 128 KiB; existing obvious-credential exclusion remains. |
| Images | PNG, JPEG, or WebP original bytes, at most 8 MiB; TIFF input up to 64 MiB is decoded and normalized to RGBA8 PNG subject to the same 8 MiB storage limit; positive dimensions up to 8,192 per side and 16 million pixels. Header/dimension validation precedes a decoder capped at 128 MiB allocations. Copy/paste writes stored encoded bytes and their native pasteboard type (PNG for normalized TIFF). |
| Files | Up to 64 local `file:` URLs, with URL input and stored JSON each bounded to 64 KiB. Only URL parsing and current filesystem metadata/existence checks occur; referenced file contents are never opened, copied into the database, or previewed. Each URL is written as its own pasteboard item on reuse. |
| Selected preview | First decoded image/frame downscaled to at most 256 × 256 and encoded as RGBA8 PNG; at most 384 KiB PNG before base64. Search does not contain thumbnails or originals. |

- Capture remains off by default. Existing persisted native consent is authoritative; no browser preference enables capture. Enable/clear/delete baseline the current pasteboard without re-reading or immediately recapturing it. Only subsequent revisions are considered; repeated unchanged images are not repeatedly decoded.
- Read pasteboard-wide and every item’s privacy type markers before any payload. Private, concealed, transient, autogenerated, remote clipboard, and known password-manager markers are skipped. Compare pasteboard change count after reads to reject torn snapshots. Unmarked sensitive images, filenames, and text may still be saved; this is not content-based image redaction.
- Prefer native file references, then supported image types, then UTF-8 text. Mixed multi-item content is rejected rather than silently dropping items. HEIC/GIF-only, legacy filename-only, HTML-only, and other unsupported content is skipped with a settings notice. TIFF-only image clipboards are supported; PNG/JPEG/WebP representations take precedence when also advertised. HTML with a plain-text representation remains eligible for text capture. No OCR or rich HTML preservation is implemented.
- `NSData` length is checked before copying bytes into Rust. The OS pasteboard provider itself may materialize data when requested; this code cannot control the provider’s allocation.
- Up to 1,000 entries and 128 MiB total logical payload/label storage. Duplicate payloads refresh the stable ID without losing pins. Evict the oldest unpinned entries to satisfy capacity/bytes; never silently evict pins. If pins alone prevent accepting a new entry, retain all history and report the limit.
- The same database file is migrated transactionally from text v1 to rich v2. Text, IDs, pins, timestamps, consent, retention, and the AUTOINCREMENT high water survive. A one-time VACUUM removes the old duplicate text index and enables incremental vacuum; migration needs temporary free space and fails closed on error.
- Image blobs and file URL arrays live in SQLite rows, not sidecar files. Retention, delete, clear, and disable atomically remove their payloads with the rows. Existing 1/7/30/90-day retention and pinned exemption remain. SQLite uses DELETE journaling, FULL synchronous writes, secure_delete, Unix 0600 database permissions, and a 192 MiB steady-state database page cap. Freed pages are reused and opportunistically compacted; transaction journals and migration/VACUUM temporarily require additional disk space. These settings do not promise encryption or erasure from snapshots/backups.
- Explicit copy writes a validated stored payload. Paste validates Accessibility permission, captured target PID/window identity, and target liveness before touching the clipboard; it rechecks the foreground app/window before posting the paste shortcut. The native write acknowledges its pasteboard `changeCount`, which is compared immediately before posting; a changed revision cancels paste and restores the Prism window without retrying or overwriting the newer clipboard. This is a last-moment guard, not an atomic OS transaction spanning the check and destination consumption. Failure never injects into another target. If activation fails after copy, the message explains the item is already on the clipboard. File references are checked while preparing each action outside the global history mutex, then consent, generation, and entry existence are revalidated before proceeding; the native write consumes that prepared payload without another filesystem check. Capture validates references before locking and rechecks generation before storing metadata. A destination app may still reject the format or observe a file changed after validation.

Action-time image and filesystem preparation for history copy/paste runs off the command/UI thread, with at most two preparations admitted. Slow preparation retains its permit until it returns, so repeated requests cannot create an unbounded blocking-worker backlog. The history mutex is released before this work; consent and entry existence are revalidated afterward.
