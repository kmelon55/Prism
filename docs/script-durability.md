# Script run durability

Script runs retain bounded local summaries and output across renderer reloads and native app restarts. Recovery never launches a command. After a native restart, any saved `running` record becomes `interrupted`; Prism does not reattach to, signal, or claim to resume an old process. An interrupted script may already have produced side effects or may have outlived the app, so the panel asks users to review those effects before explicitly choosing **Run again**.

## Storage and startup integration

During Tauri setup, initialize the existing managed registry before serving script commands:

```rust
let scripts = app.state::<script_commands::ScriptCommandRegistry>();
if let Err(error) = scripts.initialize(app.path().app_data_dir()?.join("script-runs-v1.json")) {
    eprintln!("Script history initialization failed: {error}");
}
```

`initialize(PathBuf) -> Result<(), String>` is the only new setup API. Register the existing `list_script_command_runs`, `start_script_command`, `get_script_command_run`, and `cancel_script_command` commands as before. No dependency changes or additional command registration are required. The script worker does not own `lib.rs`; the coordinator has integrated this setup wiring.

The app-data JSON file has a versioned schema and stores at most 32 runs, with at most four active foreground runs and at most one active run per registered script. Each output stream captures at most 64 KiB of raw bytes; decoding invalid UTF-8 can expand the displayed string. Native and renderer caches also evict completed runs first. Stored identity mappings cover at most 2,048 discovered scripts and preserve opaque IDs across restarts and discovery-order changes; paths remain native-only. Removing a script from configured discovery removes its identity mapping, so re-adding it later may allocate a new ID. IDs are monotonic and are not reassigned to unrelated scripts.

Before a process starts, its initial record must be saved successfully. Active runs checkpoint once per second and checkpoint again at terminal completion. Writes use a private temporary file, file sync, atomic rename, and parent-directory sync on Unix; Unix files use mode `0600`. Readers reject history larger than 64 MiB before JSON parsing and reject unsupported schema versions and oversized record counts. Corrupt history is preserved and initialization fails; execution and recovery fail closed until initialization succeeds. A native app restart retries initialization after the underlying issue is fixed.

An abrupt exit can lose output since the last successful checkpoint. A disk failure does not rerun or cancel a process: terminal state and its persistence error are published together, and **Retry saving history** requests `get_script_command_run` for that same ID. That read retries only the failed checkpoint. The last successful durable record may therefore be reported as interrupted after restart if its final checkpoint failed. A startup failure does not silently replace an unreadable history file with an empty history.

## Timeout metadata

Set the timeout in the script's metadata and refresh script commands:

```sh
#!/bin/sh
# prism:name=Generate report
# prism:timeout=120
printf 'Starting report\n'
```

The default remains 10 seconds. Accepted values are whole seconds from 1 through 3,600; zero, negative, fractional, malformed, and larger values block execution with a metadata error. Metadata scanning remains bounded to the first 8 KiB and 64 lines. `# @raycast.timeout 120` is also accepted by the existing alternate metadata parser. `timeoutSeconds` is exposed on command summaries and snapshots. The form shows the current configured limit, while a historical timeout displays the limit used for that run.

The legacy `run_script_command` also goes through the bounded run registry and uses this configured timeout. Existing Unix process-group cancellation, timeout termination, reaping, and bounded output draining are retained. Cancellation is terminal only after native termination completes; a cancel request can initially return `running`.

## Privacy and interaction

Arguments are never serialized to disk, snapshots, or renderer session state. Password input drafts clear on submit. For any script declaring a password argument, **both entire output streams are omitted from durable history**, including terminal result copies, to avoid persisting raw, encoded, or partial password echoes. Live output is still available during the native process lifetime; recovered snapshots expose `outputWithheld` and the panel explains why output is absent. Other scripts' bounded output is stored locally as generated by the script.

Snapshots expose `running`, `success`, `failure`, `cancelled`, `timedOut`, and `interrupted`, along with `startedAtMs`, `timeoutSeconds`, `persistenceError`, and `outputWithheld`. Recovery is read-only and restores terminal state without polling. An explicit **Run again** is required for an existing terminal session; password fields must be entered again. Renderer reload recovery polls only runs that the same native process reports as running.

Retries are operation-specific: **Retry start**, **Retry cancel**, **Retry status check**, and **Retry saving history**. Successful ongoing observation does not erase a cancellation error. A delayed observation cannot regress terminal cancellation. No code path automatically retries execution.
